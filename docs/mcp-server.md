# Agent-facing server (`python -m kumosql mcp`)

[Plain-language version](../docs_simple/mcp-server.md)

One stdio [Model Context Protocol](https://modelcontextprotocol.io) server for an agent that works on a Dataform project. It loads the project once, keeps it in memory and answers **one question per call** with a **bounded answer**: about 2 KB by default, with counts, what it could not determine and why, a next step, and the argument that asks for more. This is step 4 of the [roadmap](roadmap.md#4-one-agent-facing-server) (the first four tools), step 6 ([preflight, comparison and on-demand profiling](roadmap.md#6-preflight-comparison-and-on-demand-profiling), four more) and the [analyst-agent trial](https://github.com/wojoe-444/KumoSQL/issues/872) (`list_tables`, `clean_query`, and reading `${ref()}` in drafts) and [`project_checks`](https://github.com/wojoe-444/KumoSQL/issues/881), then [`join_profile` and grain for sources](https://github.com/wojoe-444/KumoSQL/issues/881) (the same trial) and `rows_filtered` ([#881](https://github.com/wojoe-444/KumoSQL/issues/881)).

```
python -m kumosql mcp PROJECT [--source-schema FILE] [--assume-grain TABLE=COL[,COL]]... [--docs DIR]... [--malloy DIR]... [--boundary FILE] [--profiles DIR]
                           [--cache-dir DIR | --no-cache] [--refresh-interval SECONDS] [--warm-wait SECONDS]
python -m kumosql mcp --git URL [--branch B] [--refresh]
python -m kumosql mcp                      # saved data profiles only, no project
```

`PROJECT` is what `pipeline-report` takes: a Dataform project folder, a folder of `.sql` files or the JSON of `dataform compile --json`. The server answers `initialize` at once and parses and analyses the project in the background (about 3 seconds for the 106-model public project in the fixtures); the first question waits for it, and every later one is served from memory (a column trace or an impact answer takes 10 milliseconds or less). `--assume-grain` declares which columns identify a row of a table the project does not define, for example `--assume-grain logs.events=insert_id` (repeatable; the table is written as the other tools take it). Such a grain is reported as `declared`, never as derived, and a table or column that does not exist is dropped with a line on stderr. Without it the server uses what the project itself shows: grains derived from the queries and `assertions: {uniqueKey}` in the models' configs, and the sources listed under [Where a grain comes from](#where-a-grain-comes-from). Register it with an MCP client as the command `python -m kumosql mcp /path/to/project`. Messages are JSON-RPC 2.0, one per line; progress logs go to stderr, never stdout.

## The questions

| Tool | The question | Arguments | Built on |
| --- | --- | --- | --- |
| `describe_table` | What is this table? | `table` | `profile_pipeline` (grain, row scope, column meanings), lineage filters, inferred role, readers, saved data profiles |
| `trace_column` | Where does this value come from, and which rows reach it? | `table`, `column` | `Pipeline.trace_column`, `explain_lineage` |
| `impact` | What breaks if I change this? | `table`, optional `column`, optional `change` | `Pipeline.assess_change` |
| `find_existing` | Does a table for this already exist, or one I can roll up? | one of `table`, `sql`, `expression` | `find_overlaps`, `find_rollups`; for `expression`, [`expression_search`](../src/kumosql/expression_search.py) |
| `find_tables` | Which table should I use? | `need` (or `has_columns`), optional `column`, optional `kind` | table profiles, tags, saved data profiles, the saved catalog |
| `compare_queries` | Is my rewrite still the same query? | `left`, `right`, optional `time_limit`, optional `respect_row_order` | `prove_statements`, the SMT prover and its counterexample search |
| `check_query` | Is this draft sound before I run it? | `sql`, optional `dry_run` and `project` | type inference, tie detection, fan-out from table grain, BigQuery-specific static checks, the BigQuery dry run (on request) |
| `profile_table` | What do the values look like? | `table`, optional `project`, `run`, `save`, `file`, `duckdb`, `columns`, `sample_percent`, `row_filter`, `top_values`, `show_values` | `kumosql.data_profile` behind its byte cap |
| `list_tables` | What is in this project, and which tables have this shape? | optional `kind`, `tag`, `folder`, `name_contains`, `min_reads`, `max_reads`, `min_readers`, `max_readers`, `min_depth`, `sort` | the loaded project's graph, kinds, tags and file paths |
| `clean_query` | Can this query be tidied, and what exactly changes? | one of `sql`, `table`; optional `inline_ctes`, `time_limit` | the verified cleanup rules of `python -m kumosql rewrite-sql`, the equivalence prover and the independent checkers |
| `project_checks` | What is wrong with the repository itself, before any warehouse is asked? | optional `check` | the loaded project's declarations, `disabled` flags and loader diagnostics ([`kumosql.project_checks`](../src/kumosql/project_checks.py)) |
| `join_profile` | What does joining these two tables on these keys do? | `left`, `right`, `keys`, optional `split_by`, `top`, `project`, `run`, `duckdb` | one query built by [`kumosql.mcp_join_profile`](../src/kumosql/mcp_join_profile.py), run under the same gate and byte cap as `profile_table` |
| `rows_filtered` | Where are rows dropped on the way to this column? | `table`, one or both of `column` and `predicate` | the lineage filters behind `trace_column` (`kumosql.lineage_filters`), the SMT prover for a predicate |

Every tool also takes `max_bytes` (the size bound, 1,000 to 20,000, default 2,000) and `offset` (where the answer's main list starts). **`${ref()}` in a draft.** `check_query` and `compare_queries` read `${ref("table")}`, `${ref("dataset", "table")}` and the same with `resolve` as that table of the project, so a draft written inside a Dataform project needs no editing; `refs_read_as` lists each as `ref(x) = dataset.table`. A reference to no table (or to several) is refused with the close table names, like every other tool. `${self()}`, `${when(...)}` and other expressions stay unread: `check_query` answers `cannot_check` naming the first of them, and `compare_queries` answers `unknown` because the text is not SQL.

A `table` is a model or declared source of the project, written as the full key, `dataset.table` or the bare table name, in any case. A name that matches several tables, or none, is not guessed: the error lists up to five close tables in `candidates`, the closest first (a misspelling puts its likely target first), and `next` names the best one once.

- **`describe_table`** returns the table's kind and file, its grain (`["id"]`, `"single row"` or unknown with the reason), whether its rows can be compared, one line per column (`name = meaning`, or `name = ? (reason)` when the meaning is unknown), the conditions in its own query once each (not once per column), the tables it reads and the tables that read it, columns nothing reads, and whether a saved data profile exists (with the resource to read). A grain that is not derived from the query carries `grain_origin`, in words: `declared uniqueKey on model X`, `primary key in docs file F (section S)`, `Malloy primary_key in F (source S)`, `--assume-grain`; a derived one says `derived from the query` (over a source whose grain is stated, it names that statement). A source (a table the project does not build) with no stated grain but a saved measurement shows `grain_assumed`: `near-key on (id): 3 duplicate rows in 5,000 (0.06%), 0% null; from the saved data profile of <day>, an assumption, not a declared grain`.
- **`trace_column`** returns the one-hop sources, the ultimate source columns, the models the value passes through (nearest first) and the filters and joins that limit its rows, written **once per model**. `column` may name a field inside a STRUCT column (`payload.user.id`). `complete: false` plus an `unknown` entry means a step could not be followed, so the sources are a lower bound.
- **`impact`** takes `change` of `drop_column`, `rename_column`, `change_expression` or `drop_table` (default `drop_column` when a column is given, `drop_table` otherwise). It lists the models that break, change values, may change behaviour or break indirectly, nearest first, then the readers that could not be analysed (grouped by reason), and the files to open. `safe_to_delete` is always `unknown`: readers outside the project (query history, dashboards) are not visible.
- **`find_existing`** compares the table (or a proposed `SELECT` written against the project's tables) with every other table. It returns `verdict`: `found` (same meaning, contains or partial matches, best first), `rollup_possible` (a finer-grain table could be aggregated), `none_found` (with how many tables were compared) or `cannot_tell`. When nothing can be compared the answer is a few lines saying so, naming what blocks it (the target's own grain or column meanings, or the other tables') instead of listing every table that was skipped.
- **`find_tables`** takes a need in plain words (`need="daily revenue by customer"`), and optionally a `column` name (an exact name counts most) and a `kind` (`table`, `view`, `incremental`, `source`, or a role: `fact`, `dimension`, `bridge`). It returns up to five candidates, best first, each with its `score`, why it matched (`name`, `columns`, `tag`, `meaning of`, `saved profile columns`, `saved catalog`), how many of your words matched, its grain, how many models read it and what is unknown about it. The ranking is fixed word matching (lower case, singular, camelCase and underscores split, a shared start of four letters counts half) with fixed weights: a word in the table name 4, in a column name or tag 2, in the dataset, a tracked column meaning, a saved profile or the saved catalog 1, counted once at its best place; an exact `column` adds 6; ties go to the table more models read, then to the name. The same question always gives the same answer. Assertions are not offered. A table with an unknown grain or unknown column meanings can only be matched by name, and the answer says how many tables that is. `offset` pages the candidates. It reads only what the loaded project, the saved data profiles and the saved catalog hold: no BigQuery, no language model.
- **`find_existing` with `expression`** asks "is this CASE ladder (or other expression) copied across the project?" Pass one SQL expression written with the project's column names. The answer is a count and the models: `6 copies, 2 variants in 6 models: 'GOLD' maps to NULL (30 in variant 1)`. Copies are found inside any select expression, join condition, `WHERE`, `HAVING`, `QUALIFY` or `GROUP BY` of any readable model, and inside larger expressions (a CASE inside `COALESCE(...)`, the argument of an aggregate); an answer names the place of each (`p.ds.orders (column n)`, `(WHERE in cte x)`). Copies are the same after normalization: source qualifiers and aliases, case, spacing, redundant parentheses and the order of comparisons are ignored, `CASE x WHEN 'A' THEN 1` equals `CASE WHEN x = 'A' THEN 1`, and a missing `ELSE` is `ELSE NULL`. Branch order is ignored only where it cannot matter: when every branch compares one expression with constants (`x = 'A'`, `x IN ('A', 'B')`, `x IS NULL`) no two branches are true together, so the ladder is a mapping from constants to results. Any other ladder keeps its order (the first true branch wins), and a ladder that differs only in order is its own variant, with the difference named. A **variant** is a group of copies that are identical after normalization: for a CASE, the same set of branch conditions with different results, default or order; for any other expression, the same expression with different literals. Each variant lists its copies, its models (eight at the default size, more with a larger `max_bytes`, `+N more` after that) and one line on what differs from the closest other variant; `same_as_yours` marks the variant identical to the expression you gave. A ladder that has only some of your branches is listed under `partial` with the branches it lacks, one that has all of yours and more is `extends`, and one that shares at least half of the branches is `overlap`; none of them counts as a copy. Models whose SQL could not be read, models with pre or post operations or an incremental branch (only the main query is searched) and expressions the normalizer could not follow are listed under `unknown`. The index of normalized sub-expressions is built once per session from the parsed trees the project already holds, in the background warm-up (about half a second for 106 models; code copied between models is normalized once, so a 400-model project of similar models took about 0.3 s), and every later question reuses it. It is plain JSON-serialisable data (`ExpressionIndex.to_json()`: one part per model, each tagged with a hash of the model's SQL and template expressions), and `build_index(pipeline, saved)` reuses the part of every model whose hash is unchanged, so a cache can save it later. The server itself keeps the index in memory only: it writes nothing, in the project or anywhere else, and the lookup sends no query to any warehouse.
- **`find_tables` with `has_columns`** answers "is there a link table, or a view over one, that carries both keys?": `has_columns=["order_id", "customer_id"]` (two to four names; do not combine with `need` or `column`; `kind` still filters). It lists up to five tables, models, views and sources that carry every key, each with how each key matched: `name and meaning` (the column has that name and means the same value as the key elsewhere in the project), `meaning only: the column is renamed` (a different name, the same source column behind it, as in a view that renames the keys) or `name only` (the name matches, but the project does not show the same meaning, or shows a different one: it may be another thing with the same name). Tables matched by both come first, then narrower tables, then the ones more models read. A key name that stands for more than three different things in the project is matched by name only and the answer says so; write `table.column` to pin a key to that table's column. Only tracked meanings count (a column of a table with no known lineage is matched by name only).
- **`compare_queries`** takes two queries written against the project's tables. It runs the structural and algebraic proof first (what `prove-sql-equivalent` runs), and when that does not settle it the SMT prover with the columns, keys and NOT NULL columns the project declares, which can also return a database on which the queries differ. `verdict` is `equivalent` (with `proof`: `unconditional`, or `given declared project facts`, and the `assumptions` the proof rests on), `not_equivalent` (with a `counterexample`: made-up rows per table, at most three each and clipped, and what each query returns on them) or `unknown` (with the reason; unknown is not a claim that the queries differ, and is never turned into a proof). Rows are compared as bags; `respect_row_order=true` also requires the same `ORDER BY` (only the structural proof checks that, so more pairs stay unknown). Column types and names are not compared: the answer's next step is `check_query` with a dry run. `time_limit` is the cap in seconds (default 10, from 1 to 60): the check runs in a forked process that is killed at the cap, and a check that does not finish is `unknown`. It touches no database and no network.
- **`check_query`** takes a draft `SELECT` written against the project's tables (a table name, `dataset.table`, or a Dataform `${ref("table")}`; see above) and runs the offline checks in one call. `types`: the output columns and their types ([type inference](type-inference.md); a project model has no stored column types, so most read `?`) and the errors the query certainly has (an unknown column, an ambiguous name, a UNION of different widths). `ties`: places where the result can change from run to run because rows tie (`ROW_NUMBER` with a non-unique `ORDER BY`, `LIMIT` without a total order, `ANY_VALUE`, `ARRAY_AGG`, ...), judged with the grain of the project's tables as unique keys (`ties_judged_assuming` says which). `fan_out`: an `INNER` or `LEFT` join whose condition does not match every grain column of the joined table, a join without a condition, judged for project tables, CTEs and subqueries with a known grain; with a `SUM`, `COUNT` or `AVG` in the same `SELECT` the finding says the totals would count rows more than once. `RIGHT` and `FULL` joins are listed under `unknown`. A joined table whose grain the project does not show (a warehouse table or view) is judged in order from a [stated grain](#where-a-grain-comes-from) (listed in `fan_out_judged_assuming` with its origin), then from a [saved measurement](#join_profile-and-key-measurements) (no repeats on the join columns: no finding, and the measurement is listed as assumed; repeats: a finding with the counts and the day, worded `near-key` when at most 1% of the rows repeat), and otherwise it is `unknown` with the exact call to run: `join_profile left=<table> right=<table> keys=<columns>`. No extra call is needed once a measurement is saved. Each entry of `findings` is `{check, what, fix}`; `verdict` is `problems_found`, `no_problems_found` (the checks that ran found none; the answer says this is not a guarantee) or `cannot_check` (the draft does not parse, is not a `SELECT`, or has a `${...}` expression other than `ref()`, which the answer names). **The BigQuery dry run runs only with `dry_run=true` and an explicit `project`** (the project is never guessed; either argument alone is refused). It is BigQuery's free planning step: no data is read and nothing is billed. The answer then has `dry_run.estimated_bytes` against the `byte_cap` of Settings → Scopes (over the cap is a finding with its fix), BigQuery's own error as a finding if it rejects the query, and the column types BigQuery returns (`column_types_from`). With no credentials, no network or an unreachable BigQuery the answer says `not checked: <reason>` under `unknown` and still returns the offline checks. Without `dry_run` the tool never touches the network.
- **`check_query` static checks** (`checked` lists `static`) catch what BigQuery rejects or silently gets wrong, from the text alone, with no network (`kumosql.bq_static_checks`). They exist because `SELECT x AS new FROM t` used to answer "no problems found" although BigQuery refuses a reserved word as an alias. Each finding's `check` is the rule name below, and it comes before the type, tie and fan-out findings because it usually stops the query from running at all. A rule reports only what it is certain of; where it cannot decide, the answer lists the spot under `unknown` with the count and the reason, never a silent pass.

  | `check` | Finds | Fix it names | Cannot decide (listed under `unknown`) |
  | --- | --- | --- | --- |
  | `reserved_alias` | a [GoogleSQL reserved keyword](https://cloud.google.com/bigquery/docs/reference/standard-sql/lexical#reserved_keywords) (`NEW`, `NULLS`, `GROUPS`, ... 96 words, a frozen set in the module) used without backticks as a column, table, subquery, `UNNEST` offset or CTE alias; the text is checked, so a backticked alias is never reported | quote it with backticks or rename it | an alias whose position cannot be matched to the text |
  | `subquery` | `IN (SELECT ...)` or a correlated subquery that reads another table inside a `JOIN ... ON`; a correlated scalar subquery with `LIMIT`; a correlated scalar subquery whose only link to the outer query is `<`, `<=`, `>`, `>=` or `<>` | join to a pre-aggregated CTE, or use a window function | every other correlated subquery (BigQuery de-correlates many, such as an equality-correlated `EXISTS`), counted as "correlated subqueries not classified" |
  | `not_in_null` | `NOT IN` over a list that contains `NULL` (it never returns a row), and `NOT IN (SELECT col ...)` when a schema snapshot says `col` is nullable | `NOT EXISTS`, or `IS NOT NULL` in the subquery | `NOT IN (SELECT ...)` with no nullability: the project has no schema snapshot, so the answer says "nullability unknown". A `WHERE col IS NOT NULL` in the subquery, a literal or `COUNT` is known not to be `NULL` |
  | `limit_reread` | `LIMIT` without `ORDER BY` in a CTE that is read more than once (each read may return different rows); a one-row `SELECT` and `LIMIT 0` are exempt | order by a unique key, or materialize it once | a CTE name defined twice |
  | `duplicate_column` | `t.*` (or `*`) plus an explicit column or alias with a name the star already outputs (BigQuery renames one to `name_1`), judged from the columns the project declares, case-insensitively; `EXCEPT` is honoured | give the alias another name, or `t.* EXCEPT (name)` | a star over a table whose columns the project does not declare, or a `USING` join |
  | `case_branch` | a `CASE` branch that can never be reached: `WHEN NULL`, a constant-false condition, a branch after an always-true one, a contradictory condition (`x = 1 AND x = 2`), or a branch whose rows an earlier branch already takes (numbers, `=`, `IN`, `BETWEEN`, `<`, `>` on the same column); an `ELSE` after an always-true branch or after `IS NULL` plus `IS NOT NULL` | remove or fix the branch | nothing is reported when a condition is not fully understood (functions, `<>`, string ordering, different spellings of a column) |
  | `system_time` | `FOR SYSTEM_TIME AS OF` on only some references to one table of the draft | the same clause on every reference, or read it once in a CTE | none |
  | `cte_shadow` | a CTE read in `FROM` without an alias, with the name of a column of another table in the same `SELECT`, when that column is read unqualified: the name resolves to the CTE's row (a STRUCT) | qualify the column, alias the CTE, or rename it | a neighbouring table with undeclared columns |

  Nullability comes from an optional hook on the session, `column_is_nullable(table_key, column) -> bool | None` (a schema snapshot with `is_nullable` provides it); with no hook, or when it answers `None`, `not_in_null` for subqueries stays under `unknown`. The reserved-word list is the one of the GoogleSQL lexical reference (the ZetaSQL copy has one more word, `GRAPH_TABLE`, which is left out). The `subquery` shapes come from analysts' experience with BigQuery's "correlated subqueries that reference other tables are not supported unless they can be de-correlated" and join-condition errors; no test reaches BigQuery, so a dry run remains the final word.
- **`check_query`** takes a draft `SELECT` written against the project's tables (a table name, `dataset.table`, or a Dataform `${ref("table")}`; see above) and runs the offline checks in one call. `types`: the output columns and their types ([type inference](type-inference.md); a project model has no stored column types, so most read `?`) and the errors the query certainly has (an unknown column, an ambiguous name, a UNION of different widths). `ties`: places where the result can change from run to run because rows tie (`ROW_NUMBER` with a non-unique `ORDER BY`, `LIMIT` without a total order, `ANY_VALUE`, `ARRAY_AGG`, ...), judged with the grain of the project's tables as unique keys (`ties_judged_assuming` says which). `fan_out`: an `INNER` or `LEFT` join whose condition does not match every grain column of the joined table, a join without a condition, judged for project tables, CTEs and subqueries with a known grain; with a `SUM`, `COUNT` or `AVG` in the same `SELECT` the finding says the totals would count rows more than once. `RIGHT` and `FULL` joins and tables whose grain is unknown are listed under `unknown`. Each entry of `findings` is `{check, what, fix}`; `verdict` is `problems_found`, `no_problems_found` (the checks that ran found none; the answer says this is not a guarantee) or `cannot_check` (the draft does not parse, is not a `SELECT`, or has a `${...}` expression other than `ref()`, which the answer names). **The BigQuery dry run runs only with `dry_run=true` and an explicit `project`** (the project is never guessed; either argument alone is refused). It is BigQuery's free planning step: no data is read and nothing is billed. The answer then has `dry_run.estimated_bytes` against the `byte_cap` of Settings → Scopes (over the cap is a finding with its fix, see below), BigQuery's own error as a finding if it rejects the query, and the column types BigQuery returns (`column_types_from`). With no credentials, no network or an unreachable BigQuery the answer says `not checked: <reason>` under `unknown` and still returns the offline checks. Without `dry_run` the tool never touches the network.
- **Cost and access in `check_query` and `describe_table`** ([`kumosql.mcp_cost_access`](../src/kumosql/mcp_cost_access.py)). Every request is a free BigQuery dry run, sent only in a call that passes `dry_run=true` and a `project`; the dry-run job is created in that project, never in a source project, and no query is ever run.
  - *Estimate and access.* With a dry run the answer has `dry_run.estimated_bytes` against `byte_cap` and a `sources` list with one entry per table the draft reads: `{table, access: readable | denied | unknown, scan_bytes?, note?}`. When the whole query plans, every table it reads is `readable`; the full-scan size of up to three sources is learned with one `SELECT *` dry run each (a draft that is exactly `SELECT * FROM table` needs none). When BigQuery answers `Access Denied` for a table it names, that table is `denied` (a `check: access` finding with its fix; the message also covers a table that does not exist in that location) and each other source is probed the same way. An access error that names no table (the billing project cannot run jobs) stays an ordinary `dry_run` finding.
  - *Without a connection* (no `dry_run`) the answer lists `estimated bytes and source access` under `unknown` with the reason `not checked: no connection ...`, and still reports any denial remembered from an earlier call.
  - *Remembered for a while.* A denial, a readable table with its full-scan size and a dry-run estimate (by normalized SQL: spacing, comments and keyword case do not matter) are kept per account for one hour (`KUMOSQL_ACCESS_TTL_SECONDS`; `0` turns it off). The account is the non-secret namespace of [`query_context`](../src/kumosql/query_context.py); a different account sees none of it. Later `check_query` answers (with or without `dry_run`) and `describe_table` say `not readable with the current account (cached, N min ago; recheck with refresh=true)` and send nothing; an estimate answered from memory says `dry_run.cached`. `check_query refresh=true` (needs `dry_run=true`) asks BigQuery again, which is how a granted access is noticed before the hour is over.
  - *On disk, optionally.* `KUMOSQL_ACCESS_CACHE_FILE=user` keeps the memory in `kumosql/access-cache.json` of the user cache folder (`XDG_CACHE_HOME`, else `~/.cache`), or give another path; a path inside the project folder is refused, because the server never writes into the repository. The file holds the table name, the outcome, a byte count and a time under a hashed account namespace: no credential, token, SQL or error text. A write first merges what other server processes wrote and replaces the file in one step, so several servers can share it.
  - *`describe_table`* shows `full_scan` (bytes, from a dry run, with its age) once known. Until then it lists `full-scan size` under `unknown` ("unknown until a dry run has been made") with the exact `check_query dry_run=true project=<billing project> sql="SELECT * FROM ..."` call as its next step; `access` appears when a denial is remembered.
  - *Over the byte cap* is a `dry_run` finding that states the estimate and the cap and gives the cheapest remedy: name the columns instead of `*` (or drop columns not used), then filter on the partition column; `LIMIT` does not cut bytes. It does not suggest raising the cap, which is the budget owner's decision in Settings → Scopes.
- **`list_tables`** is the whole-project question the per-table tools cannot answer. Each table is one line, `name | kind | reads N (+n src) | read by N | depth N`, where `name` is `dataset.table`, `reads` counts the other models of the project it reads (`+n src`: declared sources it also reads), `read by` counts the models that read it (assertions included) and `depth` is the number of models between it and a source (0 reads no model). With no argument it is the overview: counts of models, sources, models nothing reads and kinds, the commonest tags, then the first page. Filters combine: `kind`, `tag`, `folder` (a text inside the model's file path, such as `definitions/alerts`), `name_contains`, and the bounds `min_reads`, `max_reads`, `min_readers`, `max_readers` (`max_readers=0` lists what nothing reads) and `min_depth`. `sort` is `name` (default) or `readers`, `reads`, `depth`, largest first and ties by name. Assertions and operations without an output are not tables to use and are left out unless `kind` names them. An unknown `kind` is refused with the kinds the project has. It reads only the loaded project (no BigQuery, no model), and the same call always gives the same list. `offset` pages the list. `count_only=true` answers with the counts alone (about 150 to 350 bytes), for "how many" questions.
- **`clean_query`** runs the product's cleanup rules (`remove_trivial_predicates`, `remove_redundant_parentheses`, `deduplicate_ctes`, `remove_unused_ctes`, `remove_redundant_distinct`; see [rewrite rules](rewrite-rules.md)) on a draft (`sql`) or on a model's own file (`table`, read from inside the project folder and never written) and answers with a **diff**, not the whole query. `inline_single_use_ctes` is off unless `inline_ctes=true`, because it reprints the query as nested subqueries and changes its layout. Every change is checked by the equivalence prover and an independent checker, as `python -m kumosql rewrite-sql` does. `verdict` is `cleaned` (`changes` lists `rule xN`; `diff` is a unified diff with one line of context and whitespace kept, paged by `offset`; for a draft whose cleaned text is at most 1,200 characters, `cleaned_sql` is the text itself), `already_clean` (nothing to change; when some rules left the text as written because it holds a `${...}` expression other than `ref()`, pipe syntax or a Jinja tag, an `unknown` entry says so instead of claiming it is clean), `unproven` (something would change but a proof was not established: **no diff is offered**) or `cannot_clean` (the text does not parse, or the time cap `time_limit`, default 20 seconds and at most 60, was reached). It touches no database and no network.
- **`project_checks`** answers "is the repository itself consistent?" without a warehouse or a schema snapshot, from the loaded project only. Four checks, each a group with `count`, three `examples`, what it means and its `fix`: `declared_and_built` (a name declared as a source, by `declare()` or `type: "declaration"`, that the project also builds as a model: Dataform rejects the duplicate action name), `disabled_read_by_enabled` (a model with `disabled: true`, which Dataform compiles but never runs, that an enabled model or assertion reads: its table may never have been built or may be stale), `declared_in_several_datasets` (one table name declared in two or more datasets, so a one-argument `ref("name")` is ambiguous) and `defined_twice` (two files publishing the same table; the loader kept the later one). An identical declaration repeated is one table and not a finding. `check` limits the answer to one group and lists up to 20 examples. The answer always says under `unknown` that the deployed state is not read: a table that was never built, is older than its model or has another partitioning is not visible without a warehouse or a schema snapshot. The same facts appear in two other tools: `describe_table` carries one `project_check` line for a table concerned (declared and built, disabled and read, reads a disabled model, declared in several datasets), and `check_query` adds an `unknown` entry when the draft reads a disabled model, a model that reads one, a name declared and built, or a declared source the project does not build (whether it exists in the warehouse is not checked), so a draft over such tables is never a bare "No problems found". "Inactive" here means `disabled: true`; a model left out of every production schedule is not detected.
- **`rows_filtered`** answers "why don't my example rows show up?". It lists, **in path order** (the table first, then each model upstream), the conditions that can remove rows on the way to `column`: `WHERE`, `QUALIFY` and `HAVING`, the `ON` of every inner join, and `EXISTS` / `IN (subquery)` conditions (`kind` is `where`, `qualify`, `having`, `inner_join`, `semi_join` or `anti_join`). Each entry has the `model`, the `clause`, the `kind`, `on` (`column`: the condition reads the column or a column it is copied or computed from; `joined`: it reads other columns, such as the key of a joined table; `constant` or `unknown` for a condition that reads no column or whose columns could not be worked out) and `in` (the CTE or subquery it is written in, when not the main query). The conditions of the tables that are joined in are followed too: a filter inside a calendar model that an inner join keeps you from escaping is listed as `joined`. Conditions that cannot remove rows are not listed but counted under `counts.not_listed`: the `ON` of an outer join (rows without a match stay), filters inside a scalar subquery in the select list, and the right side of `EXCEPT`. The lineage extraction is the one `trace_column` uses; no query is parsed a second time.

  **`predicate`** is one simple condition on the table's columns for the rows you expect, such as `status = 'cancelled'` or `region_code = 3` (no subquery, aggregate, window or time-dependent function; it may be given with or without `column`). Each listed condition then gets a `result`. `can_remove` means the equivalence prover **proved** that no row satisfying the predicate passes the condition (the predicate and the condition can never both be true), so the rows are gone at that model. `may_remove` means the condition can drop such rows and it cannot be told whether it does: it reads another table (a join or `EXISTS`), another column, an aggregate or a window, or the prover did not settle it; `why` says which. Conditions the predicate provably passes are only counted (`keeps`). A condition that cannot be read at all, or depends on the time it runs, is listed under `unknown` with the reason, never left out. A condition is compared with the predicate only when the lineage can follow its columns exactly: through plain copies in CTEs and derived tables to one table the model's query reads once, and from there through unchanged copies to the table's column. A changed copy (`UPPER(status)`), a table read twice (a self join) or a column that cannot be followed is an opaque value to the prover, which can make an answer less certain and never more. At most 40 conditions are compared per answer; the rest are `may_remove`, and an `unknown` entry says how many. `unknown` also says that the rows a source table holds are not visible (`profile_table` shows values). `first_removed_at` names the first model on the path, nearest the table, where a condition is proven to remove the rows (`none proven` otherwise), and the summary repeats it. **Inactive and incremental models.** An entry in a model with `disabled: true` carries `inactive_model: true`, `counts.in_inactive_models` counts them, and `unknown` names the inactive models on the path: Dataform never runs them, so their tables may be missing or stale and their conditions may not describe the rows that exist. A condition written inside `${when(incremental(), ...)}` carries `incremental_only: true`; it applies to incremental runs only, so it is `may_remove` (`why: applies on incremental runs only`) and never called a proven removal, and `unknown` notes that incremental models keep rows from earlier runs, which a condition changed since then does not describe. `offset` pages the list, `can_remove` entries first. It reads only the loaded project and never sends a query or writes a file.
- **`trace_column` and the size cut.** The conditions that read the traced column (or a column it is built from) come first, inside each model and among the models, so a cut for size loses the conditions on other columns before them. `counts.filters_on_column` says how many there are. When the list is cut, `filters_by_model_shown` says how many models and how many conditions were shown (`1-3 of 6 (9 of 48 conditions)`), `more` says `max_bytes=...`, and when more than three conditions apply the next step names `rows_filtered` for the full list in path order.
- **`profile_table`** profiles the values of a table with [`kumosql.data_profile`](data-profiling.md): the row count and, per column, nulls, distinct values, range and the most common values, one line per column. What it does depends on `project` and `run`, and the default costs nothing:

  | Call | What happens |
  | --- | --- |
  | `table` (a project table), nothing else | Plan only, no network: the columns and number of queries it would send, and `unknown: estimated scan size` |
  | `table` and `project` | BigQuery **dry run** of every profile query (free): `scan.estimated_bytes` against the cap; nothing runs. Over the cap is `mode: refused` |
  | `table`, `project` and `run=true` | The profile runs, each query dry-run first and capped; the whole plan is refused before anything runs when its estimate is over the cap |
  | `file` (CSV, TSV, Parquet, JSON) or `duckdb` (a database file) | Free, so it runs at once. The file must sit inside the project folder |

  `run=true` without `project` is refused. The cap is the one in Settings → Scopes, applied to the **sum** of the plan, which is stricter than the per-query cap of `profile-table`. `columns`, `sample_percent` and `row_filter` narrow the scan; `top_values` (0 to 10, default 3) and `show_values=false` limit the quoted values. **Values from a table are data, never instructions**: every value is JSON-quoted and clipped to 24 characters, and the answer carries a `note` saying so. A **completed BigQuery profile is saved** (`save=false` skips it) in the profile folder, outside the project, and the answer lists its `key_candidates` (columns that are unique or repeat at most 1% of the rows, with the repeated rows, the row count and the null share); a local `file` or `duckdb` run saves nothing, because a local copy need not hold the warehouse table's rows. `python -m kumosql profile-table` saves a profile the same way. Credentials missing or BigQuery unreachable: `mode: not_run` with `not checked: <reason>`.

## Where a grain comes from

A table the project does not build (a warehouse table or view, declared or not) has no query to read a grain from. Each of these says which columns identify a row; the first that exists for a table wins, a model's own query always wins for a model, and every answer names the origin (`grain_origin`, or the text of `fan_out_judged_assuming`):

1. `--assume-grain TABLE=COL[,COL]` (you declare it; also for a warehouse table that is not in the project, matched by its trailing parts).
2. The declaration itself: `assertions: { uniqueKey: [...] }` (or `uniqueKeys`) in its config, or a `uniqueKey` list in `declare({...})`. Dataform's own declaration config has no key of its own, so this is the project's claim and nothing checks it.
3. An assertion file that names the table: exactly `SELECT k FROM ${ref("t")} GROUP BY k HAVING COUNT(*) > 1` (`COUNT(1)`, `COUNT(k)` and `>= 2` read the same). A `WHERE`, join, `QUALIFY`, `LIMIT` or `DISTINCT` makes the claim about a subset of rows, so such an assertion is not read.
4. A Malloy source: `source: s is conn.table('dataset.table') extend { primary_key: id }` in a folder given with `--malloy DIR` ([`kumosql.malloy_keys`](../src/kumosql/malloy_keys.py), on the shared [`kumosql.malloy_reader`](../src/kumosql/malloy_reader.py): only a source built directly on a table, not one built on another source; nothing else of Malloy is read).
5. Markdown docs in a folder given with `--docs DIR` ([`kumosql.docs_keys`](../src/kumosql/docs_keys.py)): a `Primary key: a, b` line, or the rows marked `yes`, `x`, `true`, `pk` or a check mark in a column table whose header has a `Primary key` or `PK` column, inside a section whose heading (or, before any heading, whose file name) names exactly one table. Prose, list items that are not plain column names and sections naming no table are ignored.

A model's own `assertions: { uniqueKey }` still fills the grain of that model when its query shows none; Markdown and Malloy keys and assertion files do the same for a model whose query leaves the grain unknown, and never replace a grain the query shows. A key naming a column the table does not have is dropped with a line on stderr. All of these are statements somebody wrote, not facts checked against data; the answers say `declared`.

## `join_profile` and key measurements

`join_profile left=orders right=wh.order_events keys=order_id split_by=order_week` answers the questions that otherwise take several rounds of hand-written SQL, with **one query** over the whole population (no `LIMIT`, no sample, each table grouped by its key once, so the same call gives the same numbers). `keys` is a column used on both sides, or `left_column=right_column`, comma separated (at most 6; a row with a null in any key column never matches). `left` and `right` are project tables, `project.dataset.table`, or `dataset.table` (read in the project's default project); `split_by` is a column of the left table (`right.column` for the right). The answer carries, per side, the rows, the null-key share, the number of repeated key rows and the most rows per key, and the share of rows that find a partner; then `cardinality`, the inner-join row count, and, with `split_by`, the top `top` (default 5) values by unmatched rows. `cardinality` is `1:1`, `1:N` (the right side repeats keys: a join repeats left rows), `N:1` (a lookup: the left repeats keys, the right is unique), `N:M`, or `unknown` when a side has no non-null key. It is judged on whole tables (a side is unique when no key value repeats on it), so a repeat only among unmatched keys still counts; the inner-join row count shows what the join actually returns.

It follows the gate of `profile_table` exactly:

| Call | What happens |
| --- | --- |
| no `project` | Plan only, no network: the SQL (one piece per common table expression, cut like any list when it does not fit; `max_bytes` shows it whole) and what it returns |
| `project` | BigQuery **dry run** of the one query (free): `scan.estimated_bytes` against the cap; nothing runs. Over the cap is `mode: refused` |
| `project` and `run=true` | The query runs under the cap. The result is saved in the `join-profiles` folder inside the profile folder (outside the project; never inside it: a profile folder inside the project is not written to) |
| `duckdb` (a database file inside the project folder) | Free, runs at once, is not saved |

A run's saved result gives key measurements: for each side, the table, the key columns, the rows, the null-key rows and the repeated rows. `profile_table` runs give the same for every single column. A measurement is a count on one day, not a constraint: wherever `check_query` or `describe_table` uses one it says so, with the day and the counts. Lookup rules: no repeats on a subset of the join columns means none on all of them; repeats are used only when measured on exactly the join columns (a key measured on a longer set says nothing about a shorter one; the call is offered again); a join that also pins a column to a constant is never decided from repeats on the equated columns alone. Sampled, filtered or approximate profiles are not measurements. The profile folder is the data folder's `data-profiles` or `--profiles DIR`.

## Producers and consumers outside the repository (`--boundary`)

A trace ends at a declared source and `impact` ends at the last model, but many sources are built by jobs the repository does not contain (scheduled queries, notebook jobs, legacy query tools) and many outputs are read by semantic models and BI data sources. `--boundary FILE` (YAML or JSON) names them. The file only adds knowledge: nothing it names is contacted or written, and no query is sent. Paths are relative to the file. The example is synthetic:

```yaml
producers:
  - table: lookups.region                     # a declared source of the project
    by: {kind: scheduled_query, id: "1234", url: "https://example.test/q/1234"}
    sql: external/region.sql                  # a file, or a list of snippets
  - table: lookups.segment
    by: {kind: notebook, id: nb-7}
    sql_unavailable: the notebook code was not exported
consumers:
  - {name: sales_semantic_model, kind: semantic, path: "semantic/*.malloy"}      # Malloy files, read by the Malloy reader
  - {name: legacy_report, kind: bi, path: "bi/*.lkml"}                            # any other files, scanned as text
  - {name: weekly_dashboard, kind: dashboard, sql: external/dashboard_source.sql}  # parsed
```

- **Producers.** `by.kind` is free text (`scheduled_query` and `notebook` are the expected ones). The `sql` (a file, or a list of snippets that each build some columns) is parsed with the normal parser and lineage as a model outside the project. `trace_column` continues from the declared source into the columns that SQL reads, and on through the SQL of further producers, in an `outside_the_project` list (`source`, `built_by`, the `file`, the columns it `reads`, `through` the other producer tables). A producer with no SQL is an `unknown` that says so: with `sql_unavailable: <reason>` (a notebook whose code was not exported) the answer reads "built outside the project by notebook nb-7; its SQL is not available (reason)". `describe_table` of the source says `built_outside_the_project` (kind, id, url) and lists the tables the job reads (`outside_reads`). A declared source the file does not name is an `unknown` ("who builds it").
- **Consumers with `sql`.** Parsed like a model, so the columns it reads are exact. `impact` lists it under `readers_outside_project` with its `effect` (`breaks`, `values_change`, ...) and `columns`; a producer's SQL that reads the target is listed the same way, with `feeds_project_models` when the project reads the table it builds.
- **Consumers with `path` (Malloy).** A path or glob, or a list. Files ending in `.malloy` are read by [`kumosql.malloy_reader`](../src/kumosql/malloy_reader.py): `read_malloy(text)` returns the sources of a file, each with its `name`, the `table` it reads (`table('ds.orders')`, or the table of the source it `extend`s, including one defined in another file of the same consumer), its `primary_key`, the `columns` its dimensions, measures, filters, keys, views and joins refer to, and its `joins`. A source reading the target table and referring to the target column is reported as `reads (Malloy)` with the source names and the file. It does not compile Malloy: it cannot tell a column from a name defined elsewhere, so the answer says it can be wrong either way. Whatever it cannot read (a source built from `sql(...)`, a parent source that is in no file, unbalanced text) is listed under `unknown` and the file is then also matched as text.
- **Consumers with `path` (other files).** Scanned as text. A file that names the table (`dataset.table`, any case, backticks allowed) **and** the column as a word is a reader `reads (by text)`, with the `evidence` file; for `drop_table` and `describe_table` the table alone counts. A file that names the column but not the table is an `unknown`, not a reader. A text match can be wrong in both directions (a column name in a comment, a table reached through a view or a variable).
- **Unreadable is unknown.** A consumer whose pattern matches no file, or whose file is not text, is over 2 MB or cannot be read (a pattern matching more than 200 files is scanned in part), appears under `unknown` with the reason, one line per reason however many consumers share it. It is never counted as having no reader.
- **Many readers.** `impact` shows `counts.outside_readers` and `counts.outside_by_kind`, then as many readers as fit the bound, exact readers first. When there are more outside readers than readers inside the project, `offset` pages `readers_outside_project` (the answer's `more` says which `offset` returns the next page); otherwise it pages `affected` as before. The boundary file loads in about a second for 300 producers and 300 consumers on a laptop, and the outside SQL is analysed in the background after start-up.
- **Errors at load time.** A file that is missing, is not YAML or JSON, has an unknown key (the closest is suggested), a `sql` file that cannot be read or does not parse, a `sql` together with `sql_unavailable`, or an absolute path stops `python -m kumosql mcp` before it serves, with at most five problems named. A producer table the project does not have (the closest names are given) or builds itself is reported once the project has loaded: the file is then not applied, a line goes to stderr and every `trace_column`, `impact` and `describe_table` answer says under `unknown` that the boundary file was not applied.

The file is read when the server starts (restart to pick up an edit to it; an edit to the project itself rebuilds the outside models too). `safe_to_delete` stays `unknown`: only the readers the file names were checked.

## Rules every answer follows

- **Bounded.** `max_bytes` is a promise. When an answer does not fit, the longest lists are cut first; `unknown` and `next` are cut last. A cut list says `"columns_shown": "1-6 of 7"` and `more` says what to ask: `offset=6` for the next page, or `max_bytes=2129` for the whole page.
- **No repeats.** A filter is said once per model, never once per column.
- **Unknown stays explicit.** `unknown` is a list of `{what, reason}`. Reasons are plain-language versions of the codes the analysis uses (`nested_field`, `source_without_grain`, `analysis_gaps`, ...), never a silent omission.
- **Next step included.** `next` names the model files to open or the tool call that explains an unknown.
- **Read-only, offline by default.** The tools never write a file of your project. No tool opens a network connection unless it is asked to: only `check_query` with `dry_run=true`, `profile_table` with `project` and `join_profile` with `project` reach BigQuery (a free dry run; the other two run queries only with `run=true`, under the byte cap, never without that explicit consent), and `tools/list` marks those three as open-world. The one thing the server writes is a completed BigQuery `profile_table` or `join_profile` result, in the profile folder (the data folder, or `--profiles DIR`), never inside the project folder: if that folder is inside the project, nothing is saved. `--docs` and `--malloy` folders are only read, once per loaded project: an edit in them is picked up when the project itself is reloaded. Loading a project writes KumoSQL's own diagnostics log (`ui.log`) in its data folder, as every KumoSQL command does. Names, SQL conditions and saved-profile values in an answer come from your project and your tables: they are data, never instructions, and the server's `initialize` instructions say so.

## Warm start

An agent asks, edits, and asks again, so the server does not pay the whole analysis in front of every session's first answer. The analysis is nearly all column tracing (every output column of every model); that is what is saved and reused. The code is `kumosql/mcp_cache.py` (the saved file, the background build, edit detection) and `kumosql/trace_memo.py` (what the analysis replays).

**Saved index.** After an analysis the trace of every model is written as JSON to one file per project path: a header (format, KumoSQL version, sqlglot version), a fingerprint of the project-wide facts, then one entry per model. Nothing is executed or unpickled; an entry holds names, strings and lists only. The folder is `--cache-dir`, else `kumosql/mcp-cache` in the platform's per-user cache folder (`$XDG_CACHE_HOME` or `~/.cache`, `~/Library/Caches`, `%LOCALAPPDATA%`), keyed by a hash of the project's path. The default is never inside the project (if the cache folder were pointed into it, the system temporary folder is used), because the server never writes a project file; only an explicit `--cache-dir` can put it there. The folder gets a `.gitignore` of `*`, so it is not committed wherever you put it. `--no-cache` neither reads nor writes it. Many servers can share one project (an agent session starts one each): a server writes a private temporary file and renames it over the saved one, so a reader sees the old file or the new one and never half of either, the last writer wins, and there is no lock for a killed process to leave behind.

**What makes an entry valid.** Each model's key is a hash of its own definition (SQL, config, target, path) and of the keys of every model it reads, so it changes when the model or anything upstream of it changes, and for nothing else. The file as a whole is valid only for the same KumoSQL and sqlglot versions and the same project-wide facts: the set of table names, the declared sources and every table schema known before tracing (including columns looked up in the saved catalog, so a changed catalog traces again), the default project and dataset, the models that define procedures or table functions, and the lineage time limits. A project setting change, or a model added, removed or renamed, therefore traces every model again; an edit to the SQL of one model traces that model and the models downstream of it. A replayed entry is placed in the analysis exactly where tracing would have put it, so the analysis equals a cold start (the tests compare the records, their order and the diagnostics, not only the tool answers).

**What is never reused.** A model on a dependency cycle; a model that a time limit cut short (`lineage_skipped`) and everything downstream of it; the whole project when a model writes into another model's table (`MERGE` or `INSERT` operations) or has an `INSERT` with no column list. These are traced on every start. A file that is missing, unreadable, corrupt, from another version, or whose entry does not decode is ignored (that entry only, for a bad entry) and written again; it never stops the server.

**Background build.** `initialize` answers at once and the index is built in a thread. A tool call while it runs waits up to `--warm-wait` seconds (default 3; `0` never waits). If the index is still not ready, the call is answered, not failed:

```json
{"answer": "index warming, 41% done: no answer yet, ask again in about 6 s",
 "index": {"state": "warming", "percent": 41, "stage": "tracing columns", "reason": "after the server started", "ask_again_in_seconds": 6},
 "next": ["Ask the same question again in about 6 seconds. ..."]}
```

No tool answers from an unfinished analysis. The percent is 2 while loading, 5 to 90 while tracing (by models done), then 92 and 96 for profiles and roles, and 100 when ready; `reason` is `after an edit to the project` during a rebuild. When the build ends the server logs `index ready: N models analysed, M replayed from the saved index` on stderr. `describe_table` and the other tools answer as before once it is ready, and answers then carry no `index` field. Resources (saved data profiles) are not held back.

**After an edit.** On each tool call the server compares the project's files (`.sqlx`, `.sql`, `.js`, `.json`, `.yaml`, `.yml`) with the last build: first by size and modification time, then by content hash, so touching or re-saving a file without changing it rebuilds nothing. `--refresh-interval SECONDS` bounds how often the files are looked at (default `0`: on every call, which for a few hundred files costs milliseconds because unchanged files are not read). There is no refresh tool or argument: a call made after an edit finds the edit. On a change the project is read again in the background, only the changed models and those downstream are traced again, and the new index replaces the old one when it is complete, so an answer never mixes the two. Calls during that time wait or answer `index warming` as above.

## Saved data profiles

The server also serves the resources that [`profile-mcp`](data-profiling.md#agents-the-mcp-server) serves: two per saved profile, `kumosql://data-profile/<name>/summary.md` and `profile.json`, read-only, from the data folder or `--profiles DIR`. `python -m kumosql profile-mcp` keeps working unchanged (resources only, no tools). `describe_table` points at the saved profile of a table when one exists.

## Adding a tool

A tool is one function registered in `kumosql.mcp_tools` (or another module listed in `TOOL_MODULES` in `kumosql/mcp_server.py`):

```python
@tool("find_tables", "Find a table", "Which table should I use?", {"need": {"type": "string"}}, required=("need",))
def find_tables(session, args):
    answer = Answer("...")          # summary, then .fields, .counts, .add_list(...), .unknown(...), .next(...)
    return answer
```

`session` is the loaded project (`session.pipeline()`, cached `profiles()`, `roles()`, `records()`, name resolution with `session.resolve(...)`). The size bound, paging, argument checking and error answers come from `kumosql.mcp_answers`, so a tool only builds the answer. Raise `ToolError(message, [next steps])` to refuse a question with a way forward.

## Limits

- On the 106-model public project 45 of 626 column meanings are unknown and 49 tables have no known grain (41 `source_without_grain`, 8 `grain_not_in_output`); `find_existing` there answers for 54 of 106 tables and says `cannot_tell` for the other 52, naming the blocker. Tables that read the same log table cannot be told apart by grain unless the project, or `--assume-grain`, names the columns that identify an event and the view keeps them. Values of an unnested array (`UNNEST(...) AS item`, then `item.name`) and fields of a computed value stay unknown. See [what `find_existing` can decide](#what-find_existing-can-decide-on-this-project).
- `--boundary` is only as good as the file: a producer, a dashboard or a semantic model nobody listed is invisible. The text scan sees table names written as `dataset.table`, not a table reached through a view, a variable or a differently named dataset, and it does not read a column list from a wildcard (`SELECT *`) in a text file. The Malloy reader is a small reader, not the Malloy compiler: `columns` is every name a source's definitions use that the source does not define, so a dimension that shadows a column of the same name can hide a read of it, and a source built from `sql(...)` is `unknown`. Producer and consumer SQL is read with the project's table columns only, so an unqualified column over a table the project does not know stays unresolved (an `unknown`). `pipeline-report` and the other commands do not take the file yet.
- A declared grain is a claim. `assertions: {uniqueKey}` is checked by Dataform when the assertions run; `--assume-grain`, a declaration's `uniqueKey`, a Malloy `primary_key` and a docs line are not checked by anything, so a wrong one makes `find_existing` match tables that differ and the fan-out check pass a join that repeats rows. Answers show it as `declared`, with its origin. The docs reader is deliberately conservative (a heading must name one table, a key must be plain column names), so a key written in another style is not found, not guessed.
- A key measurement is the table on the day it was counted. A saved near-key is used as an assumption and says so; a table that has changed since needs the call run again (`join_profile` or `profile_table` with `run=true` replaces the saved one). `join_profile` counts whole tables once, which on a very large pair can reach the byte cap: it then refuses before reading anything and a view that selects only the key columns is the way to profile it. The BigQuery paths of `join_profile` are tested against a DuckDB-backed stand-in only, like those of `profile_table`.
- `impact` does not read job history yet, so readers seen only in query history are not listed, and `safe_to_delete` stays `unknown`.
- The BigQuery paths (`check_query` with `dry_run=true`, `profile_table` with `project`) are tested against stubs only: no test reaches BigQuery. `profile_table` with `run=true` is the one call that can bill, and it is capped, so try it on a small table first.
- The static checks of `check_query` are text rules: they do not prove a query valid. On the 243 model queries of the public example projects and about 9,000 SQL strings of the test fixtures they found nothing in any BigQuery-valid query (the findings were deliberate constants and non-BigQuery fixtures). Their gaps are listed under `unknown`, and the `subquery` rules were not run against BigQuery itself.
- `check_query` does not run the query or compare its rows with anything, and models have no stored column types, so a dry run is what returns real types. The fan-out check needs a known grain or a saved measurement; on the public project 41 tables read tables the project does not define and have none until a key is stated (see [where a grain comes from](#where-a-grain-comes-from)) or measured.
- `find_existing expression=...` matches the same computation over the same column names: a copy that reads the value under another column name (`raw_code` instead of `code`) is not found, and because qualifiers are ignored a join condition `a.x = b.y` also matches `b.x = a.y`. A `WHERE` that holds your conditions plus others is matched only when the grouping of its conjuncts is the same. Ladder branches are compared as written after normalization, so `x > 5` and `x >= 6` differ. Operations and incremental branches are not searched.
- `find_tables has_columns=...` is as good as the lineage behind it: a key that is not traced to a source column can only be matched by name, and that is said.
- `find_tables` matches words, not meanings: "revenue" does not find a table whose columns are called `sales`. On the public project the top candidate for each model's own name is that model, and a need such as "intermediary activity per day" finds the right table by its name and its `day` column, but 351 of 626 column meanings are unknown there, so a better table may hide behind a name the words do not match.
- `compare_queries` proves what the prover can prove today; most real rewrites that change a join or an aggregate come back `unknown`. A counterexample is a small made-up database, not data from your tables.
- The warm start saves the column trace, which is nearly all of the analysis, not the rest. Reading the project's files and parsing the models happen on every start and every rebuild, and table profiles, roles and the other per-session results are computed again from the replayed trace (on the 106-model public project: about a tenth of a second for the read and a third of a second for the rest, against about three seconds for a cold trace). A rebuild after an edit reads every file again; only the tracing is incremental. The speed-up is therefore largest on projects where tracing dominates, and is not measured on a project of several hundred models here.
- Answers are measured in bytes of JSON, not tokens.
- The server handles one request at a time on stdin, and does not support JSON-RPC batches or cancellation.
