# Repository instructions for Claude

Direction: read [docs/roadmap.md](docs/roadmap.md) before starting work. It is the plan of record from the November 2026 review: a five-minute merge gate with benchmarks on a schedule, the prover split into its own package ([wojoe-444/Kumo_SQL_Prover](https://github.com/wojoe-444/Kumo_SQL_Prover), decided 2026-11-10), and one agent-facing server with small, bounded answers for analysts. Work on its steps in order, and do not extend the areas it lists as parked. Walter decided the three rules the roadmap left open on 2026-11-11 (the test policy, where the scoreboard lives, the plain-language twin docs), and no CI runs through GitHub for KumoSQL or the prover repository; the rules below say how.

SQLGlot standard: `sqlglot==30.21.0` is the only supported version. Walter fully approved this transition ([#716](https://github.com/walterogozaly/KumoSQL/issues/716)). The local gate and Dell full-suite runs use the matching compiled `sqlglotc==30.21.0` build once per revision. Do not restore the 26.0.0 / 30.20.0 compatibility matrix or a second routine full-suite pure-Python run. Pure Python remains usable; use `--pure` for focused diagnostics when needed. Future version changes require explicit validation and an intentional update to the pin and docs.

Keep documentation and README files up to date when your changes affect setup, usage, behavior, or developer workflows. Include those updates in the same pull request.

The README is the overview: a link to the generated scoreboard page (`docs/scoreboard.md`), a short summary per feature, the CLI table and the laptop-replica smoke test. Feature details live in `docs/` (for example `docs/ui.md`, `docs/provers.md`, `docs/pipeline-analysis.md`, `docs/rewrite-rules.md`, `docs/cost-and-change-reports.md`, `docs/dataform-repositories.md`) and one page per eval in `docs/evals/`. `docs/README.md` indexes every page and `docs/evals/README.md` indexes the eval pages and names each eval's results file; list a new page in the matching index (`tests/test_docs.py` checks both indexes and every relative link; `python tools/docs_index.py --write` adds a page nobody listed yet to a generated block). Put new detail in the matching docs page, and change the README summary only when the one-line description changes. When a README merge conflicts over a section that moved to `docs/`, apply your change to the docs page.

Write every page in `docs/` plainly: purpose first, a concrete example, and the limits of the evidence; link to recorded scores instead of copying numbers that change. A hand-written plain-language companion at the same relative path in `docs_simple/` is required only for the entry pages an analyst reads first (`SIMPLE_REQUIRED` in `tests/test_docs.py`: getting started, the agent server, the UI, data profiling, pipeline analysis, change reports, Dataform repositories, the field trial, the scoreboard and the evals index); update those with the page they explain. The older companions of other pages stay as snapshots and are not required to follow every change; they must still link back to their full page. `tests/test_docs.py` checks the entry companions, both sets of indexes, reference links and relative links.

No CI runs through GitHub, for this repository or the prover repository. The check is local: `python tools/run_tests.py --gate` (the routine tier held to a 300 second budget; `--evals` runs only the benchmark floors, `--no-evals` the rest; add `--label "<task>"` and `--target <test file>` for the tests your change is aimed at, so the test history can tell your failures from collateral ones, see `docs/test-history.md`). Tests must be safe to run in parallel: no shared files or module-level state between tests. When your work is complete, run the relevant tests and open a pull request. For code changes, run targeted regressions, the affected evals and `--gate` on each exact candidate before merging; the full default suite including the eval floors is a periodic local or Dell run and runs before releases, and nothing opens an issue automatically when it fails, so look at its result. Prover changes (shared prover, parser, normalization or execution code) now live in the prover repository and need broader base/candidate case comparisons and soundness guards there before merging; KumoSQL takes them by a pin bump (`pyproject.toml`), checked with `--gate` and the staying evals. Benchmarks report, they do not gate a change, except that a score must never drop without an explanation and a false proof is a bug. Record the exact SHA and the coverage of every validation; never describe a routine result as full coverage. Documentation-only pull requests may use the documentation checks without an eval run. Merge only when the applicable validation is recorded on the pull request; if a conflict blocks merging, report the blocker and leave the pull request open. See [the merge testing procedure](docs/test-history.md#merge-testing-procedure).

Benchmark scoreboard: the scoreboard page is generated from `benchmarks/results/*.json`, one file per eval. Any change that moves an eval's score, or adds an eval, must update that eval's results file (score, size, date, caveats; keep "0 wrong" honest) and run `python tools/scoreboard.py` in the same pull request. Never edit the scoreboard page by hand. If the table conflicts when merging, keep either side and rerun the script. Mention the same numbers in the eval's own docs page under `docs/evals/`. An eval that has a ledger counts only admitted proofs. The ledgers live in the prover repository (`benchmarks/admitted/` there, next to the results files): when a proven count changes, run `python tools/proof_admission.py admit <eval> --prover <prover checkout>` here and commit the ledger with the results file in the prover repository (its `tests/test_proof_ledger.py` fails otherwise; see `docs/proof-admission.md`). The tool never runs without a named checkout. A proof the command reports as false is a bug to fix, never a line to add by hand.

A change meant to leave every score alone (a refactor, a shared helper, a cleanup) should show it: `python tools/eval_diff.py` reruns every eval on `origin/master` and on your checkout and reports any eval whose answers differ.
